# 增量流：事务组装、批提交、位点与限速

## 1. 事务组装

事件按源端事务边界组装：`BEGIN` 开始缓冲，`COMMIT` 触发一次批提交，`ABORT` 整段丢弃。

| 约束 | 默认值 | 超限行为 |
|---|---|---|
| 单事务内存 | 128 MB | **当前实现：立刻报 `E1011` 并停下**——不交付这一批、位点不前进。spill 到磁盘（`--spill-dir`）仍是计划，未实现 |
| 单事务行数 | 100 万 | 同上（`E1011`） |
| 单事务告警线 | 512 MB | `tx_oversize: spill`（默认）/ `fail`；**这两个取值目前只是策略开关，既然 spill 未实现，两个都表现为「超限即报错」** |

**为什么是报错而不是硬撑**：整段缓冲的内存 ≈ 行数 × 行宽，一个 `DELETE` 5000 万行或
`INSERT…SELECT` 灌 2000 万行是真实场景；继续撑下去是 OOM（进程直接没了，看不出原因），
而 `E1011` 是可读的、带下一步的失败（拆事务 / 调上限，风险写清「调高会推高峰值内存」）。

**配置口径**（2026-11-06 定形状）：上限有两个来源，按 **`yaml 显式值 > 环境变量 > 内置默认`** 取值。

```yaml
reliability:
  tx_oversize: fail                 # 旧写法：spill（默认）| fail —— 继续有效，行为不变
  # 或
  tx_oversize:                      # 新写法：对象，可只给其中一项
    mode: fail                      # 沿用 spill | fail
    bytes: 134217728                # 单事务字节上限，最小 1 MiB
    events: 1000000                 # 单事务事件数上限，最小 1000
```

- **向后兼容**：`spill | fail` 的字符串写法**继续有效**，旧 yaml 不受影响；`job.schema.json` 用 `oneOf` 同时接受两种形状（`examples/job.yaml` 是旧写法、`examples/job-tx-oversize.yaml` 是新写法，CI 每轮都校验这两份）。
- **环境变量**：`JINLIANG_TX_MAX_BYTES` / `JINLIANG_TX_MAX_EVENTS` 仍可用，只在 yaml 没给对应项时生效。
- **实现进度**：`jobspec` 的解析**已支持两种形态**（旧字符串与对象都能 import/export，旧写法导出后仍是字符串）；`bytes` / `events` 的**运行期读取**在 B5 接（引擎 `txLimits()` 改调 `TxOversizeDoc.Limits()`，取值顺序即上面那条）——在那之前它们只被校验与保存，运行期仍取环境变量/内置默认。
- `spill` 仍未实现（见上表）：两种 `mode` 当前都表现为「超限即报 `E1011`」，区别要等 spill-to-disk 落地。

**顺序**：事务内按源顺序；跨事务按提交顺序。写入端单线程，任何并行都在源端按表拆分。

## 2. 批提交（group commit）

`batch_rows=500` 或 `batch_delay=1ms` 先到者触发；自适应策略：根据最近 10 批的目标端耗时在
`[100, 5000]` 行之间调整，目标慢就增大批、目标快就减小批（延迟优先）。

一批 = 一个目标事务 = 数据 + 位点，原子提交（见 STATE-SCHEMA）。

## 3. 位点推进

- **数据侧**：每批提交时把新位点写进 `_jl_meta`（同事务）。
- **源侧**：每 1 秒把「已提交的最新位点」advance 给源端（PG 直接用 `confirmed_flush_lsn` 的
  ack 机制；MySQL 不需要服务端 ack）。
- 未提交的批次绝不 advance -- 否则重启会跳过未落库的变更。

## 4. 心跳与延迟测量

- 源端每 10s 发一次心跳事件（无变更时也发），用于判断「是否卡住」和测量基线的端到端延迟。
- 字节 lag：PG `pg_current_wal_lsn() - confirmed_flush_lsn`；MySQL `SHOW BINARY LOG STATUS` 的文件位置差。
- 时间 lag：源提交时间 -> 目标可见时间；拿不到源提交时间时标 `estimated`。

## 5. 限速

`mode.max_ops_per_sec`（增量令牌桶，默认不限）+ `snapshot.max_read_qps`（快照每连接）。
限速以「每秒事件数」为准，不以字节 -- 因为瓶颈通常在行数而非带宽。

## 6. 特殊事件

| 事件 | 处理 |
|---|---|
| `TRUNCATE` | 目标端截断（受权限约束）；PG 10 没有该事件 -> 靠定期校验发现偏差 |
| `DDL` | 白名单四类（加列/放宽长度/加索引/可选删列）在 DDL 完成后应用；其余 -> 暂停该表并告警 |
| 表结构在同步中途变化 | 重新读 catalog，比对 `_jl_meta.schema_hash`；不兼容则暂停该表 |
| 空事务 | 丢弃，不产生批次 |
| 长时间无事件 | 心跳维持租约；60s 无心跳 -> 判定连接假死并重连 |

## 7. 重连与幂等

断线后：重新拉流（从目标库位点）-> 可能重放已提交批次 -> upsert 幂等吸收 ->
最终一致。**无主键表不能 upsert**，重放会插入重复行，因此无主键表在增量模式下只允许
`insert-only` 且必须开启定期全量校验（预检会明确告知）。
