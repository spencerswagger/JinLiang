# 冲突、死信与人工介入

## 1. 什么算冲突

有稳定主键 + upsert 语义时，冲突只发生在：**目标行已存在且与本次写入的值不同**。
无主键表不参与冲突判定（只能 insert-only）。

## 2. 四种策略

| 策略 | 行为 |
|---|---|
| `manual`（默认） | **不覆盖**，写 `_ds_conflict` 记录源/目标两版；达到阈值（默认 100 条/分钟）暂停任务 |
| `source_wins` | 用源值覆盖 |
| `target_wins` | 丢弃本次变更（记一条计数） |
| `newest` | 比较 `updated_at` 之类的时间戳；**精度取决于源列质量**（PG 提交时间默认不可得，界面要说明） |

## 3. 人工处理

```
jinliang conflicts list --job x --table orders
jinliang conflicts resolve --id 42 --take source
```
`resolve` 会写入并标记 `resolved`，同时记一条 action（谁在什么时候决定了什么）。

## 4. 死信

进死信的六类原因：类型转换失败、唯一键/外键冲突、事务超上限、DDL 被拦截时该表暂停、
无主键表在增量模式下的重复插入、目标端权限不足。

每条死信带：`position`、原始行（JSON）、原因、作业名、时间。
- 上限 `max_rows`（默认 10 万）或 `on_error_ratio`（默认 5%）-> 暂停，**绝不静默丢**。
- 恢复：修好根因后 `jinliang dead-letter retry --job x` 从最早一条按位点重放。
- 轮转：超过上限的旧记录移到 `_ds_dead_letter_archive`（可选，默认关）。

## 5. 回环抑制（二期预留）

同表双向时，每条变更带 `origin`（实例 id），写入目标端影子列 `_ds_origin`；
读到自己发出的变更直接丢弃。一期只建表结构、不启用逻辑 -- 因为同表双向本身在二期。

## 6. 不做什么

- 不做「自动修复冲突」的启发式。
- 不做跨表约束推导（比如按外键顺序重排写入）-- 需要用户显式给出表顺序或关闭外键检查。
