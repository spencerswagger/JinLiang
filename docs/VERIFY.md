# 一致性校验 `verify`

## 1. 三级校验（成本从低到高）

| 级 | 做法 | 能发现 | 不能发现 |
|---|---|---|---|
| L1 统计量 | 每块 `count(*)`、`sum(数值列)`、`sum(length(文本列))`、`min/max` | 少行、多行、数值变化 | **值互换**、重复行、文本内容被等长改写 |
| L2 签名抽样 | 每块随机抽 1%（>=1000 行）拉全行，应用侧算 `xxhash64(规范化整行)` 比对 | 值互换、内容改动 | 未抽中的行 |
| L3 差异块全量 | L1/L2 报错的块拉全行逐列比对 | 精确到字段 | -- |

**L1 为什么不用跨库哈希函数**：PG 只有 `md5`，MySQL 有 `crc32` 与 `md5`，但两者的
"行签名"数值不同源、不可直接比较。所以聚合用**可加统计量**（跨库语义一致），
真正的行级校验放在应用侧（L2/L3），服务端只负责初筛。这是有意的取舍，不是省事。

## 2. 规范化规则（两边必须完全一致）

- NULL -> 哨兵字节，与空串、反斜杠 N 区分。
- 时间 -> UTC 微秒整数；`timestamptz` 与 `datetime` 差异在映射阶段已确定口径。
- 浮点 -> 定点十进制字符串（避免二进制尾差），并记录精度。
- 二进制 -> 小写 hex。
- JSON -> 键排序后紧凑序列化。
- 字符串 -> 保持原字符集（GBK 源会先转 UTF-8），emoji 与组合字符不规范化（按码点）。

## 3. 分块与并发

按主键区间切块（与快照相同的切分器）；默认 4 并发、每连接 QPS 上限 200；
`--table` 只校验指定表；`--sample-only` 跳过 L1 直接抽查。
估算：单核 >=50 MB/s，1M 行抽样约 30 秒。

## 4. 订正

- 输出：不一致块清单 + 每块前 10 行差异（字段级）。
- `--fix` 生成并执行 upsert / delete，**先打印条数与样例再等确认**。
- 每次订正写 `_jl_conflict`（或 `_jl_repair`），留痕可追溯。

## 5. 只读保证

`verify` 默认对源与目标都只读：只用 `SELECT`，不开事务写。
`--fix` 是唯一例外，且必须先有 `plan` 输出的确认。

## 6. 校验器自测

测试里故意破坏目标库（改一行、删一行、改精度、两行互换），`verify` 必须分别报出。
